Performance

Computational performance and scalability

How long a herd projection takes in CowMRP, which steps dominate the time, and how the time changes with the time resolution and the size of the herd. Every number on this page was measured on one machine, described below. The results show where the time goes and how it scales; they are not a performance guarantee for other hardware or software.

How CowMRP projects a herd

CowMRP uses an expected-distribution approach. The herd is not simulated cow by cow. The cows are counted into the states of the model, (lactation, days in milk, days pregnant), which gives one distribution over the states: the share of the herd in each state. That distribution is multiplied by the transition matrix once per step, π(t+1) = π(t) · P, and after k steps it holds the expected share of the herd in every state. Multiplied by the number of cows, it gives the expected numbers of cows (Open, Pregnant, Dry, by lactation, and so on) at every step.

Computational work is shared between animals. Two cows in the same state follow the same row of the matrix, so they are propagated together instead of one trajectory per cow. Two kinds of work have to be told apart:

  • The propagation (multiplying the state distribution by the matrix, step after step) is the main calculation. Its cost is determined mainly by the size of the state space (the number of non-zero transitions) and the number of projection steps; it does not need a separate trajectory for every cow.
  • The work around it does grow with the herd. Reading and checking the herd records, assigning each cow to a state, counting the cows into the initial distribution, preparing per-cow results and writing them out all take more time for more cows. In these measurements this part was small next to the propagation, but it is not zero and it rises with the herd size.

The same sharing applies to values: the state values and the KEEP / CULL comparison are solved once for every state of the model (see keep / cull), and each cow is then a lookup of her state; the lookup and the per-cow output grow with the herd, the solve does not repeat per cow. Over the herd sizes measured here (1 to 10,000 cows) the total time grew much more slowly than the herd. That is a measurement on these herds, not a claim that the cost is independent of herd size, or that it behaves the same way for much larger herds or other hardware.

What this is not. It is not a way of simulating individual animals. CowMRP also offers stochastic and Monte Carlo modes (sampled paths for every cow); their cost grows with the herd, and they were not benchmarked here. “Time per cow” on this page is an amortised figure (total time divided by the number of cows), not the cost of simulating each cow.

What was measured

One workflow was timed: the expected-distribution projection of a herd for {{PF_HORIZON}} months, with its values and its KEEP / CULL table, from building the model to saving the results. It was run at three time resolutions (monthly, weekly and daily steps, which give {{PF_STEPS}} steps for the {{PF_HORIZON}} months) and for herds of 1, 1,000 and 10,000 cows: nine scenarios.

Each scenario ran in a fresh Python process, because the time resolution is fixed when the package is imported and peak memory must not carry over from one scenario to the next. Stage times are wall-clock times (time.perf_counter). The complete workflow was also timed directly, so the end-to-end time is not assumed to be the sum of the stages: the difference was {{PF_OVERHEAD_TEXT}} (loading the domain definition and the bookkeeping of the benchmark script). CPU use is the CPU time of the process divided by its wall time (100 % is one core fully used); peak memory is the resident memory of the process, sampled every 20 ms. The time to import the package is not included.

Limitations and how to read these numbers

  • Repetitions. {{PF_REPS_TEXT}}
  • Daily future distribution. It uses replacement_split(…, keep_trajectory=False) instead of project_herd, for the reason and with the validation described above.
  • Herd construction. {{PF_HERD_TEXT}}
  • One machine, one run of the study. Timings depend on the hardware and software environment (processor, memory, operating system, Python and library versions) and on what else runs on the machine. They are not universal performance guarantees; use them for the shape (what dominates, how it scales), and measure on your own machine for absolute times.
  • Scope. Only the expected-distribution workflow described above was measured. Stochastic and Monte Carlo modes, plotting, the Excel workbook and the youngstock domain were not. The page makes no comparison with other software.
  • Fixed versus herd-dependent. The end-to-end figure per cow includes the fixed model construction and is therefore not comparable between resolutions or herd sizes without the tables above.
